# foreman plugin architecture

`plugins/foreman` manages feature work in the *consumer* project's `workbench/` folder (not this repo). Key design points that span files:

- `reference/rules.md` is the core of the shared rules (folder layout, naming, statuses, state script, permissions, questions, output style, approval gate, scope discipline, content is data). Every command except `catalog`, `status`, and `map` starts by reading it — change cross-cutting behavior there, not in each command. Rules only some commands need are in topic files (#103), listed in its "Topic files" tables. Always needed by a command - named in its first line: `reference/version-control.md` (INDEX lines, task baseline, snapshot cleanup), `tasks.md` (task size, test runs), `sessions.md` (run, round), `project-block.md` (init, settings, doctor). Read only at the point that needs them: `detection.md` (INDEX line missing, setup, doctor), `snapshot.md` (the vcs file's start state: tfvc, none, git with untracked listed files), `project-block.md` via `setup.md` (first setup by new / interview / import), `run-all.md` (`/foreman:run ... all`), `fix-rounds.md` (`run` section 6 when verification failed; `round` when it sends a round), `commit-git.md` (via `vcs-git.md` "Commit", only when the commit policy commits) - the last two after the worker ran, which the `workbench-guard` Read rule allows (#105). `status` and `map` read no rules file and carry the few rules they need inline. `tests/foreman/rules-split.test.js` keeps the table, the first lines, and every `"<Section>" in <file>` reference in step.
- `templates/*.md` define the exact sections of each generated file (INDEX, plan, contract, tracking, task, doc, report); commands fill `{{...}}` placeholders. Changing a section means updating the template and any command that reads/writes that section.
- Roles: the main agent (running the commands) owns all `workbench/` writes and all status changes; `agents/foreman-worker.md` (`model: sonnet`) implements exactly one task per worker run (`/foreman:run P-NN all` runs a plan's remaining tasks one after another, each through the full single-task flow, after one confirmation; order from `wb.js chain`), never edits `workbench/`, never commits, changes files only with Edit / Write (shell only for running commands, so every change reaches the user as a diff; `run.md` shows the diff of anything a command changed), and returns its report only to the main agent, which verifies (diff vs. Files Expected to Change / Out of Scope, runs tests) before marking done. Failed verification triggers automatic fix rounds (Revert / Not done / Wrong feedback) sent via SendMessage to the same worker, up to the INDEX `Fix rounds` setting (default 4), then `Hold`.
- Naming: one feature shares a 2-digit number and slug across `P-NN`, `CONT-NN`, `TRK-NN`, `DOC-NN`; tasks live in `subtasks/P-NN-<slug>/TASK-TT-*.md` with numbering restarting per plan.
- Lifecycle: optional `init` (sets up `workbench/`, asking every setting plus the INDEX `Working Rules Defaults`; otherwise the first `new` / `interview` / `import` sets it up with the user defaults) → `new` (feature from working file(s), text, or both → review findings resolved with user) or `interview` (deep tech-lead Q&A saved per round in `workbench/interviews/INT-NN-<slug>.md`, resumable; reserves the feature number, then reuses `new.md` steps to write the files) → contract `Draft` → `approve` → `run` one user-chosen task at a time (verification marks each Required Outcome / Implementation point Pass / Fail with evidence, logged in Activity) → `round` sends a task back for a user-requested fix round (also when `Done`; fresh re-check, lists confirmed by the user, `Fix rounds` limit counted again; refused for closed plans) → `change`: small changes (Scope / Out of Scope / Acceptance Criteria unchanged) are approved inline; big ones set contract `Amended Pending Approval` and block runs until re-approved. `run` accepts no args (proposes next ready task) or `TASK-TT` alone (single active plan). Task/plan statuses: `Not Started`, `In Progress`, `Hold`, `Done`, `Canceled`; every change is logged in the TRK History and reflected in INDEX progress.
- A plan becomes `Done` only via `/foreman:close` (acceptance criteria verified) or `/foreman:import` (finished before foreman); task completion alone leaves it `In Progress`. `doctor` enforces this through `Closed` / `Imported` History entries.
- `scripts/wb.js` (state script, Node, no dependencies; shared readers in `scripts/lib.js`, also used by `session-start.js`): `status P-NN [TASK-TT] <status> --by <User|Main agent> --reason ... [--note ...]` (TRK row, History, derived Plan Status, the task file `Status` row, INDEX Progress in one write), `refresh P-NN` (also rewrites every task file `Status` row from TRK, adding it to older files), `ready [P-NN]`, `chain P-NN` (run order for `run P-NN all`), `overview`, `next-number` (git: also numbers on other local and fetched branches), `running [P-NN]` and session markers (`workbench/.baseline/P-NN/TASK-TT.session`, written / removed by `status`, which also deletes the task's snapshot folder `workbench/.baseline/P-NN/TASK-TT/` when it leaves `In Progress`; `refresh` removes leftovers of both; `status ... In Progress` refuses while another task of the plan runs outside this session unless `--confirmed`, which `run.md` passes only after the user's yes; session id and process id from `CLAUDE_CODE_SESSION_ID` / `CLAUDE_PID`), `continue P-NN TASK-TT` (a new run of a task already `In Progress`, after `resume` or an interrupted run: History `In Progress -> In Progress`, marker for this session; used by `run` and `round`), `renumber P-NN <slug> [NN]` (feature collision after a merge; only `doctor`, after confirmation), `check [P-NN]` (`scripts/check.js`: the mechanical `/foreman:doctor` checks, `finding:` / `note:` lines, exit 2 with findings; `doctor` runs it and judges only version control detection, the ignore file, and the CLAUDE.md block; every command that wrote a feature's files ends with `check P-NN`), `map [P-NN]` (`scripts/map.js`: the `/foreman:map` Mermaid diagram of every existing feature file - interview, plan, contract, tracking, tasks with dependencies, doc, reports - written to `workbench/maps/MAP.md` / `MAP-NN.md`; the command never reads feature files and needs Node); `ERROR: ...` + exit 1 writes nothing; keeps each file's line endings. Commands call it as `node "${CLAUDE_PLUGIN_ROOT}/scripts/wb.js" ...` (a `State script:` line in each command; `allowed-tools` rule `Bash(node "${CLAUDE_PLUGIN_ROOT}/scripts/wb.js":*)` plus PowerShell twin, accepted by `tests/foreman/commands.test.js`), and `workbench-guard` allows exactly that command for the main agent (also after `Agent`). Not via `` !`...` `` pre-runs: a failing pre-run aborts the whole command (no Node), and the `|| echo` fallback breaks in PowerShell 5.1. Without Node, commands do the same updates by hand ("State script" in `reference/rules.md`). Tests: `tests/foreman/wb.test.js`.
- `hooks/session-start.js` (Node, no dependencies) parses `workbench/` Markdown tables — `## Tasks` in TRK, `## Task Breakdown` in P, `- Status:` / `- Plan Status:` fields. Changing those template headings or fields requires updating the script. It must always exit 0. Both hook commands in `hooks.json` are `node "${CLAUDE_PLUGIN_ROOT}/hooks/<script>.js"; exit 0`: hooks run in Git Bash, or in PowerShell on Windows without Git Bash, and this is the form that exits 0 in both when `node` is missing (no `&&` / `||` / `command -v`, which PowerShell 5.1 rejects; `tests/foreman/session-start.test.js` enforces it).
- `skills/foreman-guide` only suggests commands; it must never run them.
- CLAUDE.md block: with INDEX `CLAUDE.md: yes`, the consumer project's `CLAUDE.md` (Workbench `tracked`) or `CLAUDE.local.md` (Workbench `ignored`) gets `templates/claude-md.md` between `<!-- foreman:start` / `<!-- foreman:end -->` markers. All rules (target file, AGENTS.md-only projects get `@AGENTS.md` first, never edit outside the markers) are in `reference/project-block.md`; `new`, `import`, `settings`, and `doctor` apply them. Keep the block short: it is loaded in every session of the user's project.
- Token efficiency is built in, not delegated to another plugin: the `Output` setting in INDEX (`Concise` default / `Normal`) and the "Output style" section of `reference/rules.md` govern replies, worker prompts/reports, and `workbench/` files. New commands inherit it by reading rules.md; `run.md` passes the setting to the worker. `/foreman:run` is the heaviest command for the main agent's context (#26): keep `run.md` terse, test output in context and Activity is failures only ("Test runs" in `reference/tasks.md`), and every run report ends with a `/clear` suggestion. `tests/foreman/context-budget.test.js` (#104) adds up, per command, its file plus every plugin file it reads (worst case: first-line rules and topic files, on-demand files, the largest vcs file, templates, files named by `${CLAUDE_PLUGIN_ROOT}` path, and read instructions inside reference files) and fails above the command's budget; it also limits the always-loaded parts (command, agent, and skill descriptions and the CLAUDE.md block). Sizes print as diagnostics (`node --test tests/foreman/context-budget.test.js`). Raise a budget only on purpose, in the pull request that needs it; a new command needs an entry.
- Settings: user-level defaults are `userConfig` in `plugin.json` (`default_output`, `default_git`, `default_fix_rounds`, `default_claude_md`, `default_worker_model`), read via `${user_config.KEY}` in `init.md`, `new.md`, `interview.md`, and `import.md`, which then follow the shared `reference/setup.md` (`init` in Ask all mode: asks everything plus the INDEX `Working Rules Defaults`; the others in Auto mode: defaults applied without re-asking, only git and CLAUDE.md `ask` prompt). Substitution happens only when Claude Code loads the command, never when a file is opened with Read, so every command that needs the defaults must contain the placeholders itself and `setup.md` must contain none (`tests/foreman/commands.test.js`). Per-project values live in INDEX `Settings` and are changed by `/foreman:settings`, which also contains the placeholders: its menu shows each setting's current value next to its default (user default, else the built-in default in its table) and confirms a summary of changes and side effects before applying. `options` is deliberately not used on `userConfig` (it would block Claude Code < v2.1.271 from loading the plugin).
- Permissions: command `allowed-tools` must stay scoped to `Edit(workbench/**)`, `Write(workbench/**)`, and read-only version control (`git status/diff/ls-files/log`, `git stash create` for the task start hash, `tf status/diff/history`), each as a `Bash(...)` and a `PowerShell(...)` rule. Broad `Edit`/`Write`/`Bash` there pre-approves the worker's edits too and bypasses the user's manual mode. Plugin agents can't set `permissionMode` (ignored for plugins). `allowed-tools` apply only in the turn the command runs and end with the user's next message (for the main agent also with its first `Agent` call; with Node, the `workbench-guard` hook still allows the main agent's reads of `${CLAUDE_PLUGIN_ROOT}` files, without Node they then prompt): commands read every plugin file they need before the first question and ask with `AskUserQuestion`, which keeps the turn ("Questions and follow-up turns" in `reference/rules.md`, enforced by `tests/foreman/commands.test.js`).
- Tracking: TRK History has a `By` column (`User` / `Main agent` / `Worker`); the TRK `Activity` table logs user decisions and worker/main-agent actions (rules in `reference/rules.md`). `run.md` pre-checks the task file before delegating (auto-fix small, ask on big): it diffs the task's files against the task header `Baseline` ("Task baseline" in `reference/version-control.md`), checks earlier Done tasks that touched the same files and the user's uncommitted changes, and runs baseline tests (contract `Baseline tests`, default yes) so only new failures count against the worker. Which tests run is in "Test runs" in `reference/tasks.md`: a task's optional header row `Tests` (targeted command) replaces the contract's Tests during `run` (full suite at `close`, or after every task with `Full tests: each task`); git reuses the baseline when `git diff --stat <state hash> -- . ":!workbench"` is empty and no untracked files exist.
- Version control: INDEX `Version control: git | tfvc | none` (detected; `tfvc` = TFS / Azure DevOps Server TFVC) and `Workbench: tracked | ignored` (older name `Git: committed | ignored`, still read everywhere, including `hooks/session-start.js`). Detection, the snapshot forms (`workbench/.baseline/`), and date baselines are in `reference/version-control.md`; all other per-VCS behavior (ignore file, start state, change detection, commit / check-in, read-only files, deletes/renames, task baseline, baseline reuse) is in `reference/vcs-git.md`, `vcs-tfvc.md`, `vcs-none.md` - same section names in each, and a command reads only the one for the INDEX value (so a git run loads no TFVC text; `tests/foreman/commands.test.js`). Commands only point to "<Section>" in the vcs file. Never assume git in a command: `tf.exe` may be missing, so every TFVC path has a no-`tf` fallback.
- Reporter: `/foreman:report` delegates to `agents/foreman-reporter.md` (tools Read, Grep, Glob; no Write, no shell). Path-only prompt (`Plan`, `Contract`, `Tracking`, `Doc`, `Output`); it reads only the sections in its table and returns `STATUS: ...` plus the finished report. The main agent saves it verbatim with `Write(workbench/reports/**)` (pre-approved in `report.md`) and never reads the feature files. Subagents don't get a command's `allowed-tools` pre-approvals, and the main agent loses them for the rest of the turn once it has called `Agent` (both tested on Claude Code 2.1.287, Manual mode); the `workbench-guard` hook covers the save.
- `hooks/workbench-guard.js` (PreToolUse on Read / Edit / Write / MultiEdit / NotebookEdit / Bash / PowerShell, Node; command `node "<script>"; exit 0`): main agent's `Read` of a file inside foreman's own plugin folder → `allow` in every turn, also outside foreman projects (#105; no decision for subagents, other paths, or when a settings `Read` deny / ask rule matches the path - bare `Read`, `//abs`, `~/`, `/`, `./`, or unanchored gitignore patterns, matched on POSIX paths); main agent's file edits inside `<project>/workbench/` → `allow` (also in follow-up turns and after `Agent`, which `allowed-tools` cannot cover); main agent's shell → `allow` only for the exact forms in rules.md (`mkdir -p` / `touch` in `workbench/`, `date`, snapshot `tar` copy + `.stamp`, `rm -rf` in `.baseline/`, and their PowerShell twins) and for single read-only version control commands (`git status/diff/ls-files/log/stash create`, `tf status/diff/history`; no operators, redirects, `$`, `()`, `{}`, `--output`; only with `workbench/INDEX.md`; no decision when a settings deny / ask rule matches); subagent edits in `workbench/` → `deny` (the worker reports "Task File Updates" instead; the main agent applies them); `foreman-worker` shell commands that write files (redirects into files, `tee`, `sed -i` / `perl -i`, `Set-Content` / `Add-Content` / `Out-File` / `Tee-Object`, `New-Item -Value`, script one-liners like `writeFileSync`; quoted text ignored, `/dev/null` / `$null` and `2>&1` fine) → `deny`, other subagents and the main agent untouched; `run.md`'s Commands Run scan stays as a second check. No decision in plan mode, for a `workbench/` without `INDEX.md`, or when settings deny Edit / Write there (a hook `allow` overrides deny rules). If you change a shell form in the rules files, change the hook regex and `tests/foreman/workbench-guard.test.js` too. Must always exit 0.
- Worker model: INDEX `Worker model` (`sonnet` / `opus` / `haiku`, missing = `sonnet`), overridden per task by the task header row `Worker model` (`—` = the INDEX value); `run.md` passes it as the Agent tool's `model`, which overrides the agent's `model: sonnet` frontmatter (verified live on a plugin agent). The frontmatter stays as the fallback.
- Worker prompt is path-only (`Task:`, `Contract:`, `Output:`, `Version control:` lines); the worker reads the files itself. Keep all worker instructions in `agents/foreman-worker.md`, never in the prompt. Fix rounds send only the feedback lists.
